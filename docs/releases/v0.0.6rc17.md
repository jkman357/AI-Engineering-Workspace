# AI Engineering Workspace v0.0.6rc17

## Scope

Reference-counted persistent Firefox input bridge per unique Firefox input thread. This continues the active v0.0.6 RC line and is not a frozen release.

## Real-machine finding from rc16

The rc16 runtime evidence separated detection from routing:

- native clicks on B1, B2, B3, and B4 were observed correctly;
- `ActiveBrowserHWND` changed to the clicked Firefox root and `SetFocus` reported the expected target HWND;
- all reproduced docked Firefox roots used the same Firefox GUI/input thread;
- after each one-shot focus transaction the WPF MainWindow remained the active/foreground window while the temporary thread bridge was immediately detached;
- the observed user failure was that text could continue routing to B3 even after clicking another Browser.

The rc17 fault model is therefore **bridge lifetime per shared Firefox input thread**, not missing native click detection.

## rc17 change

- Register every dock with `FirefoxInputCoordinator` immediately after `SetParent` and before the first root-focus handoff.
- Key bridge ownership by `(WorkspaceThreadId, FirefoxThreadId)`, not by Browser pane or Firefox HWND.
- On the first dock for a thread pair, call `AttachThreadInput(..., TRUE)` once and retain the bridge.
- On additional B# roots sharing the same Firefox input thread, increment the central bridge reference count without attaching again.
- During Browser switching, update `ActiveBrowserHWND` and call `SetFocus` on only the clicked Firefox root while the bridge remains connected.
- On Browser teardown/loss, decrement the corresponding thread-bridge reference count.
- Call `AttachThreadInput(..., FALSE)` only when the final registered dock on that thread pair has been removed.
- Keep bridge state out of `BrowserDockHost`; individual Browser panes cannot independently detach shared thread ownership.
- Use `WM_PARENTNOTIFY` mouse-down as the single native activation/focus signal. Keep `WM_MOUSEACTIVATE` diagnostic-only to avoid a second handoff for the same click.
- Retain active-Browser Show IDs/layout/maximize recovery and request-based `WM_INPUTLANGCHANGEREQUEST` synchronization.
- Continue to avoid `ActivateKeyboardLayout`, synthetic `WM_IME_COMPOSITION`, and compositor/content child-HWND enumeration or focus guessing.

## Windows manual PASS gate

Do not press the `⌖` Focus button during this gate.

1. Launch B1-B4.
2. In B3 enter `333`.
3. Click B1 and enter `111`; the new text must remain in B1 and must not appear in B3.
4. Click B2 and enter `222`.
5. Click B4 and enter `444`.
6. Return to B3 and enter `ccc`, then B1=`aaa`, B2=`bbb`. Every value must remain in the clicked Browser.
7. Repeat B1 -> B2 -> B3 -> B4 switching several times with both address-bar and Google-page inputs.
8. Switch to Zhuyin and repeat cross-pane composition/commit; switch back to English/number and continue without Focus.
9. Add B5-B8 and verify earlier Browser panes still route typing to the clicked pane.
10. Toggle **Show IDs** on/off with a Browser active, then switch to another Browser and type.
11. Close several Browser panes while others remain. Remaining panes must continue to accept routed input. Runtime log should show bridge reference count decreasing without bridge detach until the last dock on that Firefox thread closes.
12. Close the final docked Browser on the Firefox thread. Runtime log should show `Persistent Firefox input bridge detached after last dock` with `BridgeRefCount=0`.
13. Reopen B1-B4 and repeat steps 2-6 to confirm bridge recreation is deterministic.
14. If any step fails, capture `logs\runtime\AIEngineeringWorkspace_*.log` and inspect `PersistentInputBridgeAttached`, `BridgeRefCount`, `ActiveBrowserHWND`, `CurrentFocus`, `GuiFocus`, Workspace/Firefox HKLs, and native activation reasons.
