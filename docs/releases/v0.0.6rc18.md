# AI Engineering Workspace v0.0.6rc18

## Scope

Firefox native input pass-through. This continues the active v0.0.6 RC line and is not a frozen release.

## Real-machine finding from rc17

rc17 proved that the Workspace could identify the clicked Browser root correctly and that the shared Firefox thread bridge/reference count behaved as implemented. However, real-machine testing still showed a decisive mismatch:

- clicking B7 produced the expected B7 native activation and root-HWND focus state;
- typed data could nevertheless appear in B8;
- Chinese/Zhuyin input remained unreliable;
- therefore Win32 root-HWND focus is not a sufficient proxy for Firefox's internal text/IME target when multiple reparented Firefox top-level windows share one Firefox GUI/input thread.

The rc18 fault model is **Workspace interference with Firefox-native focus routing**, not missing Browser detection.

## rc18 change

- Normal Browser mouse activation is observation-only. `WM_PARENTNOTIFY` records the active B# pane and promotes its WPF z-order, but does not call `SetFocus`.
- `WM_MOUSEACTIVATE` remains diagnostic-only.
- Remove the rc17 persistent `AttachThreadInput` bridge and all per-thread bridge reference-count ownership.
- Docking a Firefox root does not automatically force root focus after `SetParent`.
- Keep one explicit recovery primitive for `⌖ Focus`, `TabIntoCore`, and Workspace-driven keyboard navigation: temporary `AttachThreadInput`, root `SetFocus`, immediate detach in `finally`.
- Do not enumerate/rank Firefox compositor/content child HWNDs and do not attempt to reverse-engineer Firefox's internal focus manager.
- Make Workspace toolbar buttons and Browser pane chrome buttons non-focusable / non-tab-stop so mouse commands such as Show IDs, Auto Fit, Add Browser, maximize/restore, Focus, and Detach do not intentionally become keyboard-focus owners.
- Maximize/restore keeps deferred native refit/repaint but no longer performs automatic Firefox root-focus recovery.
- Input-language HKL differences are diagnostic evidence only. rc18 does not post `WM_INPUTLANGCHANGEREQUEST`, call `ActivateKeyboardLayout`, or synthesize IME composition.

## Windows manual PASS gate

Do not press `⌖ Focus` during the normal-interaction gate.

1. Launch B1-B4 and click directly in each Firefox address bar or Google input.
2. Enter distinct English/number text in B1, B2, B3, and B4. Text must remain in the clicked Browser.
3. Switch to Zhuyin and compose/commit Chinese text in at least B1, B2, and B3; switch back to English/number and continue.
4. Add B5-B8. Repeat distinct input in every Browser.
5. Specifically click B7 and type. No character may appear in B8 or any other Browser.
6. Click B8, then return to B7 and type again. Routing must follow the native click without pressing Focus.
7. Toggle **Show IDs** on/off and immediately continue typing in the Browser that already had a text field active.
8. Toggle Auto Fit / Free Layout and maximize/restore Browser panes; continue direct Firefox clicks and typing without Focus.
9. Close several Browser panes, reopen them, and repeat B# switching. No stale Browser may receive later input.
10. Repeat Chinese/Zhuyin composition after add/close/reopen and Show IDs transitions.
11. Only if normal pass-through fails, press `⌖ Focus` once as a recovery diagnostic and capture `logs\runtime\AIEngineeringWorkspace_*.log`.
12. Runtime evidence should show `NativeInputMode=PassThrough`, `PersistentInputBridgeAttached=False`, no normal-click `SetFocus` recovery, and no input-language synchronization request posting.
